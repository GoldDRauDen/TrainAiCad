# 521031-03 — a QA-only run looked like a make job

**FACT.** The user asked for QA only (10 codes; the drafter's `521031-03_Quyen.dwg` plus the per-code exports in `gui\521031-03\*.dxf`). The run called `python tools/job.py init 521031-03 --source ...` (needed before `job.py qa`), which wrote `make/census_<code>.json` for all 10 codes; Claude then saved its PDF renders (p1..p7) into `make/` and left five ad-hoc scripts (cmp/dump/ann/hdr/sum_data) in `QA/`. The work folder read as a make job.

**ROOT_CAUSE.** `job.py init` had one mode: it always created `make/` with the census skeletons, so QA had no state of its own. `QA_REVERSE.md` did not say what the audit target is (the `gui\<job>\*.dxf` exports are drafter output, easy to take for customer DATA), what counts as an error (production profile vs notes / text style), nor where the result goes; the markup tool lived in `luan_app/`, outside the job tools.

**LESSON.** QA is an error hunter: it reads the drafter's DWG and its `gui\<job>\*.dxf` exports (drafter output, not customer DATA) against the PDF / customer DATA, knows the make rules routed by the census, and never builds or redraws. Only the production profile counts; notes and text style are not errors; `dx` / `hl` only by meaning (dx = mirrored pair, hl = grain direction). Start with `job.py init --qa` (job_state `"mode": "QA"`, census in `QA/`, no `make/`, deliver refused); renders and scratch files go to `QA/`. Output into the job's `AI_L\`: `<JOB>_AI_QA.txt` (`<code> PASS` / `<code> FAIL: <short reason>`, all pass → `ALL_PASS`) and, on any FAIL, `<JOB>_AI_QA.dxf` drawn by `tools/qa_markup.py` (failing profile copied out, red circle + leader + note per faulty spot). Tests: `tests/test_job_qa_mode.py`, `tests/test_qa_markup.py`.
